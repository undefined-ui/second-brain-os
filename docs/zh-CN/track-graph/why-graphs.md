# 为什么需要知识图谱

智能体的记忆问题不在于存储，而在于事实到来时彼此相连，存储后却变成了平铺的条目。知识图谱保留这些连接：实体是节点，关系是有类型的边。于是，“X 与 Y 有什么关系”就变成一次图遍历，而非猜测。

本手册讨论一般意义上将图谱用作智能体记忆；第二大脑指南中的[图谱章节](../05-graphs/graph-basics.md)则讨论知识库特有的用法——把双向链接视为边、带类型的链接，以及 Obsidian 的关系图谱视图。

<a id="what-vector-rag-cannot-do"></a>

## 向量 RAG 做不到什么

嵌入检索擅长回答一种形态的问题：“找出听起来像这段话的段落。”但在另外两类问题上，它会以可预见的方式失败。

- **多跳问题。** “我的哪些客户在使用同事提醒我要警惕的那个框架？”答案不存在于任何单个文本块中，而在于事实之间的连接。相似度搜索会找出两边的片段，再让模型凭空补出中间的桥梁。
- **全局问题。** “今年我读过的所有内容里，反复出现的主题是什么？”答案是整个语料库的属性，而不是任选五个文本块的属性。

图谱能够处理这两类问题，因为边就是你在资料导入时已经计算好的连接，而图谱中的聚类结构就是主题层。[GraphRAG](graphrag.md)正是建立在这一观察之上的模式。

<a id="what-graphs-cannot-do"></a>

## 图谱做不到什么

也要如实看到另一面。图谱的质量取决于构建它的抽取过程，而抽取会损失信息、成本高，偶尔还会出错。向量搜索不需要数据模式，能容纳任何输入，而且问题是在查询时显现，而不是在导入时就固化下来。模糊回忆——“某个关于定价的内容，好像是一集播客”——属于嵌入的领域，图谱对此无能为力。

<a id="hybrid-is-the-default-now"></a>

## 混合方案已成为默认选择

到 2026 年，这场争论基本有了结论：同时需要模糊回忆和结构化多跳查询的生产系统，两者都用。向量负责找到入口，图谱从入口向外扩展。[LightRAG](https://github.com/HKUDS/LightRAG) 和 [Graphiti](https://github.com/getzep/graphiti) 都把这种结构作为默认架构，而非可选项；Zep 这类智能体记忆系统，则将图谱视为事实来源，将嵌入视为其上的索引。设计问题已经不再是选图谱还是向量，而是图谱放在哪里、由谁写入——见[图谱存储](graph-stores.md)。

<a id="when-not-to-bother"></a>

## 什么时候不必折腾

以下情况可以跳过图谱：

- 语料库足够小，可以全部放进上下文窗口。直接阅读即可。
- 问题只是单跳查找。向量搜索，甚至 grep 级别的搜索，在成本上更有优势。
- 没有人会维护数据模式。过时的图谱比没有图谱更糟，因为它会根据旧边给出自信的答案。
- 你已经维护了一套带类型链接、经过整理的 wiki。那本身就是图谱；它由你手工构建，很可能比 LLM 抽取出的图谱更好。

判断门槛大致是：当你的问题更经常需要跨文档连接事实，而不是从单篇文档检索事实时，才值得做图谱。低于这条线，[用 LLM 构建图谱](building-graphs-with-llms.md)中的抽取流水线只会增加成本，而没有回报。
