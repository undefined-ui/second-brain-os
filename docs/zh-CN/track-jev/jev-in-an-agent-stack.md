# 智能体技术栈中的 Jev

Jev 最可信的早期用途，不是替代 LLM，而是与它并肩工作。智能体循环充满了范围小、边界明确的决策——选哪个模型、哪个工具、这是否安全、我们是否完成了——如今每个决策都要付出一次完整 LLM 调用的代价。一个才出现一周、却已在 [LangChain 的运行框架文章](https://www.langchain.com/blog/building-a-harness-with-jev)中清晰可见的模式是：把这些决策交给 System One 模型，将 LLM 留给需要语言的部分。背景见 [System One 模型](system-one-models.md)。

<a id="jev-in-front-of-the-loop"></a>

## 循环之前的 Jev

- **路由器。** Jev 对传入请求分类并分流：简单查找交给便宜快速的模型，困难情况交给昂贵的推理模型。以其声称的 70–500 毫秒延迟计算，相对于省下的调用，路由步骤几乎没有成本。
- **分流关卡。** 在智能体前放一个 `Noul` 问题（“这是否需要人工处理？”），让无用内容完全不进入循环。

<a id="jev-inside-the-loop"></a>

## 循环内部的 Jev

- **工具调用防护。** LangChain 的 `AutoModeMiddleware` 使用 Jev 检查拟议工具调用是否包含风险操作，并在执行前阻止它——这是带类型的判断，而不是让第二个 LLM 评论第一个 LLM。
- **状态检查。** “任务是否完成？”“刚才的工具调用是否成功？”“用户是否感到沮丧？”——每个都是针对会话记录的带类型问题；因为 Jev 在一次并行处理中回答全部问题，问十个问题所需时间几乎不比问一个更多。

LangChain 将这一集成暴露为 `TypeSafeClassifier`：将 `state` 和一个问题字典传给 `.invoke()`，就能得到带概率、具有明确类型的答案，再由你的代码——而不是模型——据此行动。

<a id="failure-handling-with-confidence-thresholds"></a>

## 用置信度阈值处理失败

每个答案上的概率，是这套设计的关键支撑。早期采用者逐渐形成的共同模式是：

- 为每个决策单独设置阈值，依据判断错误的代价来确定。自动批准退款可能需要 0.98，而选择一个支持队列，0.7 也许就够了。
- 低于阈值，就升级处理——交给 LLM、人工，或采用安全默认值。Jev 成为快捷路径，而非唯一的路径。
- 记录概率。Jev 不提供理由，因此你发送的状态和收到的分数，就是全部审计线索。务必保留。

有一点需要坦诚提醒：整套方案都假定这些概率确实经过校准，而这恰恰是 TypeSafe 的核心主张，迄今尚未在分布外流量上得到验证。质疑者指出，一个自信的分数，本身并不能证明预测值得信任。从保守阈值开始，用自己的标注进行测量。实际配置见[入门](getting-started.md)，任务适配性见 [Jev 擅长什么](what-jev-is-good-for.md)。
