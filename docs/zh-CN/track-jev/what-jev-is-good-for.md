# Jev 擅长什么

Jev 不是通用模型。它只会针对一段上下文回答带类型的问题，仅此而已。因此，判断是否适合很简单：你的任务能否归结为从一个有限答案空间中做选择？如果可以，它就符合 Jev 的用法。如果答案需要撰写，就不适合。背景见 [System One 模型](system-one-models.md)。

<a id="the-task-shapes"></a>

## 任务形态

- **分类。** 意图识别、工单分类、内容标注——用 `Choice` 在最多 255 个选项中选择，并提供每个选项的概率。
- **路由。** 决定哪个团队、哪个工具、哪个下游模型处理这次请求。使用同一种基本类型，只是将其接入控制流程。
- **按模式抽取。** 针对一篇文档回答一组带类型的问题：这是不是发票（`Noul`）、是哪家供应商（`Choice`）、有多紧急（`Score`）。增加问题几乎不会增加延迟，因为所有问题都在一次并行处理中回答。
- **防护。** 在智能体调用工具前检查：用 `Noul` 回答“这个操作是否具有破坏性？”，超过阈值就阻止。
- **排序与评分。** 将条目放到有序量表上——潜在客户质量、挫败程度、相关性——适用于使用 LLM 评分成本难以承受的大规模场景。

<a id="where-an-llm-still-wins"></a>

## LLM 仍然更强的地方

- 任何需要产出文本、代码或摘要的任务。Jev 完全不生成字符串。
- 无法预先枚举答案的开放式推理。
- 需要解释的任务。Jev 给你的是概率，不是理由——对于受监管环境中的审计，这是一个实际问题。
- 细致阅读。早期用户报告，Jev 会按字面理解：否定词和限定范围的词容易让它出错，计数不可靠，也不会将日期视为有序量。
- 前沿水平的纯准确率。在 TypeSafe 自己的评估中，Claude Opus 5 得分 73.1%，Jev 为 67.8%。

<a id="the-latency-and-cost-maths"></a>

## 延迟与成本计算

以下数字全部是 TypeSafe 公布的说法，并非独立测量：

- 端到端延迟为 70–500 毫秒，对比其所引用的前沿 LLM 工作流的 3–329 秒——也就是“快 40–200 倍”的范围。
- 定价为每百万输入 token 0.042 美元，输出 token 免费。在其四项工作流评估中，折算下来每个案例约 0.0004 美元；GPT-5.6 Terra 为 0.0304 美元（准确率 67.9%，耗时 10.1 秒），Claude Opus 5 为 0.1761 美元（耗时 37.8 秒）。
- 最高快 193.6 倍、便宜 444.6 倍的说法，来自 TypeSafe 能力团队自己构建、在自有机器上运行的工作流。他们承认这些是偏高的结果，目前也无法证明价格没有受到补贴。

尽可能有力地表述其价值：如果每天要做一百万次分类或路由决策，即使现实中只节省 10 倍，也会改变哪些系统值得构建。究竟节省 10 倍还是 400 倍，正是独立测试尚未确定的事。如何接入智能体，见[智能体技术栈中的 Jev](jev-in-an-agent-stack.md)；想尝试第一个项目，见[入门](getting-started.md)。
