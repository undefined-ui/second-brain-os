# 知识库变得太大

<a id="symptoms"></a>

## 症状

回答越来越慢、越来越空泛。智能体读了二十页，却给出泛泛而谈的内容。图谱像一团乱麻。你记不清某个主题是否已有覆盖，查起来比上网搜索还费时。

<a id="what-it-usually-is-not"></a>

## 通常不是哪里出了问题

不是磁盘、搜索速度或 Obsidian。它们的扩展能力都没问题。

真正的问题是检索成本。索引长到阅读本身就要占用大量上下文，智能体要么跳过它，要么把预算都花在索引上，而不是具体页面上。

<a id="first-check-it-is-size-and-not-rot"></a>

## 先确认是规模问题，而不是结构腐化

运行[指标检查](../05-graphs/metrics.md)。孤立页面比例达到百分之二十的知识库，问题不在规模，而在链接；拆分也无济于事。

真正规模大而健康的知识库，应当有较低的孤立页面比例、一个占主导的连通分量、处于合理范围的平均度，以及超过几百条目的索引。

<a id="summary-layers"></a>

## 摘要层

这是第一种修复办法，通常也就够了。在总索引与具体页面之间，为每个主题领域建立一个索引，让智能体完成三次低成本读取，而不是一次昂贵读取。参见[扩展知识库](../09-maintenance/scaling.md)。

<a id="splitting"></a>

## 拆分

按领域拆分，绝不按日期拆分。只有两个领域确实无法相互启发时，才建立两个知识库。

要接受跨领域联系不再出现的代价。那些联系往往最有意思，因此拆分应该是后期手段，而非第一反应。

<a id="archiving"></a>

## 归档

把不活跃的材料放入 `wiki/` 之外的 `archive/`。仍然可以搜索，但退出索引与图谱，而且可以恢复。

这比删除更好，因为“不活跃”只是一种判断，归档内容仍然可能重新有用。

<a id="rebuild-the-index"></a>

## 重建索引

有时只是索引偏离了实际情况：条目对应的页面已经移动，或者某次半途失败的任务新增了页面，却没有补上索引。

```
Rebuild index.md from the actual contents of wiki/. Group by type and theme, one
line of description per entry, and list gaps at the bottom.
```

成本很低，却能解决比例出乎意料地高的“知识库好像坏了”的抱怨。
