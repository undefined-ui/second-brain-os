# 停止条件

循环中最难的设计问题，不是让智能体行动，而是让它停止。智能体很乐于宣称自己尚未取得的成功，而没有出口的循环就是没有上限的账单。每个严肃的循环都配有多个独立刹车，任意一个触发都能结束运行。

<a id="goal-tests"></a>

## 目标测试

首要的停止条件，是一份可执行的完成定义：工作达到可接受水平时返回退出码 0 的脚本——测试通过、静态检查无问题、构建编译成功。如果目标无法写成脚本，你拥有的就不是适合循环的任务，而是交互会话；这完全可以，但别假装两者相同。“改进代码”无法判定终止。“`tests/` 下全部测试通过，且 `ruff check .` 没有报告任何问题”则可以。[目标测试实践页](build-goal-test.md)会用四十行 bash 将它实现。

注意其中没有什么：智能体自己的意见。“智能体说已经完成”从来不是停止条件——它是目标测试需要核验的声明，[评审器与验证](critics-and-verification.md)会进一步展开。

<a id="budgets"></a>

## 预算

目标测试停止成功的运行。预算停止其他所有情况，而你至少需要三类预算，因为它们防范的失败不同：

- **迭代次数**——为尝试次数设置硬性上限。从小数值开始；五次尝试就能解决大多数可解的问题，必须二十次才能解决、五次却不行的问题很少。
- **令牌或金额**——为每次运行设置花费上限。无界面的 CLI 会报告每次调用的成本（Claude Code 的 `--output-format json` 包含 `total_cost_usd`），因此外层封装可以累加并退出。
- **实际用时**——为整个运行和每次尝试设置超时。智能体如果一直等待挂起的命令，消耗的是数小时，而不是令牌。

预算是廉价保险；唯一的错误，是为了“给它留空间”而把预算设得过于宽松。宽松预算会把缺陷变成账单。

<a id="ratchets"></a>

## 进度棘轮

预算可能允许十轮缓慢退步。进度棘轮不会：它要求每轮都在可衡量的指标上超过此前最佳状态——通过的测试数、完成的项目数、剩余错误数——否则循环就撤销本次尝试并停止。进展必须单调向前；原地踏步就是失败。这是无人值守运行的支柱，[通宵循环](build-overnight.md)会给出具体实现。

<a id="detecting-spin"></a>

## 检测空转

有些失败很明显。空转却很安静：智能体反复做同样的搜索，生成空差异，或者一次又一次遇到同名失败测试和相同错误信息。可以通过为迭代之间的状态生成指纹来检测它——失败测试名称集合、差异的哈希值、最近执行的工具命令。连续两次指纹相同，就意味着循环没有收敛，更多尝试只会继续花掉预算。提前停止，并说明原因。

<a id="handing-back-to-the-human"></a>

## 交回人工处理

凡是不是因为目标测试通过而退出的运行，都应该以面向人的报告收尾：尝试过什么、工作树现在是什么状态、哪一道刹车被触发，以及循环掌握的最有力原因证据。升级到人工处理是一项功能。一个在第三次尝试时清楚说明失败的循环，比一个挣扎到第五十次的循环更有价值，因为报告会告诉你应该修复目标测试、提高预算，还是把任务收回自己处理。[常见模式](patterns.md)展示了无人值守变体如何将它规范为晨间报告。
