# 评审器与验证

循环的质量取决于评判者的质量。现在生成的成本很低——花很少的钱，模型就会再尝试一次——因此瓶颈已从编写代码转向证明代码能工作。无论由什么承担评审器的角色，它都会决定循环是在积累进展，还是在积累垃圾。

<a id="done-versus-claims-done"></a>

## 已完成与声称完成

模型经过训练，会让对话记录看起来像是已经收尾。“所有测试通过，功能已完成”是一段文字，而文字不是证据：智能体可能根本没运行测试，可能运行了错误的测试，也可能悄悄删除了失败的测试。由此得出的规则是绝对的：循环要检查，绝不只是询问。完成是现实世界的一种状态——退出码、代码差异、通过的流水线——必须由执行工作之外的机制来测量。这也是[停止条件](stop-conditions.md)排除智能体自身报告的原因。

<a id="code-as-critic"></a>

## 用代码做评审器

优先使用确定性评审器：测试套件、类型检查器、静态检查器和构建。它们每次运行不收额外费用，每次给出的判定相同，也无法被说服。弱点在于它们只能判断编码进去的要求，而承受压力的智能体会满足字面条件——典型操作就是削弱或删除失败的测试。因此，要让评审器处于执行者无法触及的位置：禁止智能体写入 `tests/`，或者每次验证前都从 git 恢复测试目录。能被执行者修改的检查器，算不上检查器。

<a id="llm-critics-with-narrow-rubrics"></a>

## 标准明确的 LLM 评审器

有些判断代码做不了：差异是否最小，错误处理是否真实有效而非摆设，变更是否仍在任务范围内。这时可以用第二次模型调用做评审器，但必须严格收窄范围。好的评审提示词会列出三到五条可检查规则，要求结构化判定（PASS，或带位置和修复方式的违规列表），并明确禁止评论其他任何事情。泛泛要求“审查这段代码”的宽泛评审器会产生看似合理的噪声，下一次尝试就会浪费预算追逐风格意见，而不是修复缺陷。

LLM 评审器会继承[评估手册中的 LLM 评审](../track-evals/llm-as-judge.md)所记录的全部失效模式：宽松偏差、偏爱冗长，以及自我偏好。最后一种在这里尤其重要——绝不要让模型在同一上下文中给自己的工作评分。评审器应拥有全新上下文，只看差异和评分标准，最好还使用不同的模型。[实践：评审器](build-critic.md)正是把这样的机制接在两次尝试之间。

<a id="verifier-asymmetry"></a>

## 验证成本的不对称

循环之所以能奏效，是因为检查通常比执行便宜。智能体花二十分钟编写的内容，测试套件几秒钟就能验证；这种不对称是循环的动力，因为它让你可以买下许多便宜的尝试，再为判断支付完整代价。它也告诉你哪些任务适合循环。拥有低成本、可靠验证器的工作——失败测试、可复现的缺陷、基准测试数字——非常适合循环。验证成本与工作本身相当的任务——架构品味、文字质量、产品判断——则不适合；假装适合，只会大规模生产自信的垃圾。构建任何循环前，先估算验证器的成本。如果承担不起真正的验证，就让人继续在场。
