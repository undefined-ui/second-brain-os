# 常见模式

五种循环形态不断以不同名称出现。每一种都在特定工作中有价值，也都有其支持者往往轻描淡写的失效模式。这里把两面都列出来。

<a id="run-in-a-loop-ralph"></a>

## 放进循环运行（Ralph）

Geoffrey Huntley 在 2025 年 7 月给出的原始版本是：`while :; do cat PROMPT.md | claude-code ; done`。完全没有编排——一个会话结束后，另一个会话从空白状态开始，读取同一份提示词文件和同一个仓库，通过磁盘文件接续上一次的工作。这最直接地展示了：全新上下文加持久文件，胜过一个不断退化的长会话。Anthropic 如今已在 Claude Code 仓库中以 `ralph-wiggum` 插件的形式提供它。

作者本人承认的失效模式包括：只能满足编译器、却没有实际功能的占位实现；醒来后发现代码树无法构建；以及它适合从零开始的项目——Huntley 自己说，他不会在已有代码库上运行 Ralph。Ralph 大约能完成初版的 90%，唯一的刹车是人工停止按钮。

<a id="plan-execute-verify"></a>

## 规划—执行—验证

将运行划分为阶段：一次生成计划文件，后续轮次执行各步骤，验证器为每一步把关。它适合单一提示词容易偏离方向的多步骤工作。失效模式是：计划接触现实后会过时，而忠实执行过时计划的循环会不断放大错误——验证器必须在每一步运行，而不是只在最后运行一次。

<a id="generator-critic-pairs"></a>

## 生成器与评审器配对

一个智能体负责生成，另一个独立轮次依据范围明确的评分标准判断，再将缺陷反馈给下一次尝试。重点是将执行与检查分开：实现者不能给自己打分。失效模式包括：模糊的标准让评审器变成噪声生成器；以及生成器和评审器使用同一模型、共享上下文时，也会共享盲点，最终变成互相认可。详见[评审器与验证](critics-and-verification.md)；具体接法见[实践：评审器](build-critic.md)。

<a id="tournament-best-of-n"></a>

## 锦标赛／n 次尝试择优

并行启动 n 次尝试——git 工作树能以很低的成本隔离它们——然后让验证器选出胜者。当不同尝试的结果差异很大、验证成本又很低时，这个模式很有力。失效模式包括：无论有没有好的尝试，成本都会乘以 n；而如果筛选器不够强，你只是花了 n 倍的钱买来自信的垃圾，再从中选出最自信的一份。验证成本是否明显低于生成成本，决定了这种模式是否承担得起。

<a id="overnight-unattended-runs-with-mailbox-reports"></a>

## 带信箱报告的通宵无人值守运行

设置预算、进度棘轮和分支隔离，让循环在你睡觉时工作，并留下 Markdown 格式的晨间报告：改进了什么、是什么让循环停止、哪些事情需要决策。这是这套方法的成熟形态，也是准入条件最严格的模式——需要[停止条件](stop-conditions.md)中的每一道刹车，还需要让最坏情况也平淡可控的边界。失效模式是：无人值守循环也会犯无人值守的错误，债务最终以理解债务的形式落到你身上——已交付变更的速度超过你理解它们的速度。Osmani 的提醒依然适用：构建循环时，要像一个打算继续担任工程师的人，而不是只负责按启动键的人。

<a id="choosing-between-them"></a>

## 如何选择

从具备真实验证器的最简单循环开始：[实践：目标测试](build-goal-test.md)中的普通重试循环。当“检查通过，但质量糟糕”成为常见失败时，再加入评审器。只有单个循环每次都能以清晰可解释的方式停止后，才考虑并行或通宵运行——更复杂的模式会放大已有的纪律，也会放大纪律的缺失。
