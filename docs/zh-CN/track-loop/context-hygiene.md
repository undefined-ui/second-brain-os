# 上下文清理

运行框架手册讨论了[上下文工程](../track-harness/context-engineering.md)：逐轮选择和组织模型在一个会话中看到的内容。上下文清理，是同一方法在循环层面的应用：哪些内容跨轮次、跨尝试保留，以及同样重要的——哪些内容要有意销毁。运行框架管理窗口；循环管理生命周期。

<a id="editing-within-long-runs"></a>

## 长时间运行中的编辑

长时间运行的循环，通常最先死于上下文耗尽。Anthropic 的上下文管理工作直接处理这一问题：当窗口接近上限时，上下文编辑会自动清除过时的工具调用和结果，同时保持对话流程完整。在他们的 100 轮网页搜索评估中，上下文编辑让智能体完成了原本会彻底失败的工作流，同时减少了 84% 的令牌消耗。在多步骤基准测试中，单独使用编辑就比基线提高了 29% 的表现；结合记忆工具后，提高了 39%。这一经验不局限于某一家供应商：旧工具输出是窗口中价值最低、体积最大的内容，从不清理它们的循环，就是在为垃圾付租金。

<a id="files-as-the-loops-memory"></a>

## 用文件作为循环的记忆

必须保留的状态，应该彻底放到窗口之外，存入智能体可读写的普通文件：`plan.md`、带复选框的 `TODO.md`、记录迄今最佳分数的棘轮文件。模型在运行之间会遗忘；仓库会记住。这就是 Osmani 所说的“外部状态”部分，也是所有无人值守模式背后不显眼的技巧——[通宵循环](build-overnight.md)本质上不过是一个棘轮文件、一个报告文件，再在外围套上 while 循环。了解第二大脑的读者会认出这种做法：工作记忆是暂时的，所以重要的内容都要写下来。

<a id="fresh-context-per-attempt"></a>

## 每次尝试使用全新上下文

Ralph 循环的实践者付出代价后学到了一条反直觉的纪律：两次尝试之间，要丢掉对话记录。失败尝试的记录大多是困惑的轨迹——错误假设、走不通的搜索、道歉——带到下一次尝试会造成污染，让下一次把困惑当成已确定的事实。Geoffrey Huntley 的原始循环刻意在每次迭代中从空白状态重新启动智能体；每一轮都将相同文件加入上下文，因此提示词文件和仓库成为唯一记忆，每次尝试拿到的都是干净窗口和目标。

跨越两次尝试之间间隔的，应是提炼后的信息，而不是历史：失败测试的输出、评审器列出的缺陷、当前待办状态。这正是[目标测试实践](build-goal-test.md)反馈的内容——只有目标脚本的标准错误输出，没有别的。

<a id="what-to-carry-what-to-burn"></a>

## 保留什么，销毁什么

- **保留**：目标、待办文件、上一次验证器输出、评审器判定、棘轮分数。
- **销毁**：探索过程的对话记录、大量工具输出、智能体持续发表的过程评论，以及它对进展有多好的任何说法。

检验每一项的标准很直接：一个全新、能干的智能体，看到这份内容后会行动得更好吗？验证器输出能通过这个测试。长达 40,000 令牌、记录上一次如何失败的日志则不能。清理是在替下一次尝试作决定，所以它属于循环的职责，而不是模型的职责。
