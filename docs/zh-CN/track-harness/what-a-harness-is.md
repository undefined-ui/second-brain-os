# 什么是运行框架

运行框架是围绕模型、将文本预测转化为实际工作成果的一切：循环、工具、提示词、权限以及底层连接机制。模型做决策；运行框架执行、观察，再把结果反馈给模型。同一个模型，配上不同的运行框架，智能体的表现就可能天差地别。

<a id="the-loop"></a>

## 循环

核心是一个 while 循环。把对话发送给模型。如果回复包含工具调用，就执行它们，追加结果，再循环一次。如果回复只有文本，就停止并展示给用户。诀窍就这么简单——Thorsten Ball 的[如何构建智能体](https://ampcode.com/notes/how-to-build-an-agent)用不到 400 行 Go 就实现了它。这本手册其余的内容，都是对这个循环的完善。

<a id="tool-schemas"></a>

## 工具模式

工具是供模型读取的 JSON 模式：名称、描述和带类型的参数。描述本质上也是提示词——模型通过阅读它来选择工具，所以含糊的描述会导致含糊的行为。粒度、命名和错误信息比传输方式更重要。[工具与 MCP](tools-and-mcp.md) 会详细讨论这些问题。

<a id="system-prompt"></a>

## 系统提示词

这是长期有效的指令：智能体是谁、应如何行动、环境是什么样的。生产环境的运行框架会提供数千字的系统提示词，涵盖统一风格、安全规则和工具使用约定。正是在这里，“只是一个聊天机器人”变成了“有判断力的智能体”。

<a id="permissions"></a>

## 权限

能运行 `rm -rf` 的智能体需要一道决策关卡。运行框架在模型意图与机器之间，层层加入允许列表、针对各工具的审批提示、沙箱和只读模式。有了权限系统，你才能放心让智能体无人值守地运行；没有它，你本人就是运行框架。

<a id="context-window-management"></a>

## 上下文窗口管理

窗口容量有限，而且质量会在填满之前就开始下降。运行框架决定哪些内容可以进入窗口：哪些文件、多少工具输出、何时概括旧轮次，以及哪些内容通过记忆文件跨会话保留。这就是[上下文工程](context-engineering.md)，也是优秀运行框架体现价值的地方。

<a id="why-the-harness-matters-as-much-as-the-model"></a>

## 为什么运行框架与模型同样重要

截至 2026 年的基准测试反复证明同一件事：运行框架会改变成绩。Databricks 的内部测试发现，pi 的极简运行框架在通过率上击败了更重的框架，而每轮只用了三分之一的上下文——模型相同，配套机制不同。发送臃肿上下文的框架既浪费钱，也会削弱推理；善于从工具调用失败中恢复的框架，则能完成其他框架放弃的任务。模型实验室如今会针对自己的模型调优运行框架（OpenAI 称其为“分布内”框架），这说明它们认为框架是产品的一部分，而不是外包装。

<a id="the-rest-of-the-anatomy"></a>

## 其余组成部分

成熟的运行框架还会加入钩子（在生命周期事件发生时执行的确定性脚本）、子智能体（为委派的工作提供全新上下文窗口）和技能（按需加载的指令）。[Claude Code](claude-code-as-harness.md) 是所有这些机制的参考实现；[生态概览](harness-landscape.md)则介绍其他选择。

理解一次这些组成部分，你就能看懂所有框架：它们都是同一个循环，只是外衣不同。
