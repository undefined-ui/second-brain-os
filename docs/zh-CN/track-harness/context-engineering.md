# 上下文工程

提示词工程问的是“我该用什么措辞？”。上下文工程问的是“模型此刻看到了什么，为什么？”。对智能体来说，第二个问题更重要：每个工具结果、读取的文件和旧轮次都在争夺有限的窗口，而运行框架负责选择和组织它们。Anthropic 的[面向 AI 智能体的有效上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)是这一领域的经典阐述。

<a id="the-budget"></a>

## 预算

把窗口视为预算，而不是收纳箱。注意力会在窗口填满之前开始下降——Chroma 的[上下文衰退](https://www.trychroma.com/research/context-rot)研究显示，远未达到任何硬性上限时，表现就会随着输入增长而下滑。实用原则是：只提供足以让模型行动的最少量高信息密度令牌。每增加一份内容，都会稀释已有内容。

<a id="what-goes-in-and-when"></a>

## 什么内容何时进入

- **始终保留**：系统提示词、工具模式，以及 `CLAUDE.md` 等记忆文件。让它们保持精简、稳定——稳定的前缀也能维持 KV 缓存命中，Manus [测得其成本可相差 10 倍](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)。
- **按需加载**：文件内容、搜索结果、技能正文、文档。给智能体检索工具，让它主动获取所需内容，而不是预先装入它可能需要的内容。
- **永不装入**：整个代码库、完整的 API 响应、同一条指令的十种变体。

<a id="compaction"></a>

## 压缩

长会话最终会超出任何窗口的容量。压缩会概括对话记录——决策、未完成的事项、文件路径——然后带着摘要重新开始。它在设计上就是有损的；好的运行框架会重点压缩工具结果（体积大，却很少再次需要），并保留意图。[Claude Code](claude-code-as-harness.md) 会自动执行这一操作，并提供 `PreCompact` 钩子供你控制。

<a id="memory-files"></a>

## 记忆文件

必须跨越压缩和会话保留的状态，应该放在窗口之外，存入智能体可读写的普通文件：草稿、`MEMORY.md`、待办清单。文件系统是智能体的长期记忆；窗口是工作记忆。了解第二大脑的读者会认出这个模式。

<a id="structured-outputs"></a>

## 结构化输出

当下游代码需要消费智能体的答案时，就要求它遵循模式——使用带类型字段的 JSON，并尽可能通过 API 强制执行。自由文本适合人类；结构化内容适合流水线。这也能约束模型：必填字段就是一个它无法回避的问题。

<a id="failure-modes"></a>

## 失效模式

- **上下文投毒**：一个由幻觉生成的“事实”进入对话记录，并在整个会话余下的过程中被当作真实依据。
- **分心**：深埋的指令输给了近期噪声；智能体被工具输出淹没，忘记了目标。
- **冲突**：系统提示词、记忆文件和用户的指令互相矛盾，模型随意决定听谁的。
- **膨胀**：一份无人阅读、长达 40,000 令牌的工具结果，却在之后每一轮都让你付费。

大多数“模型变笨了”的反馈，都属于这四类之一。阅读实际对话记录来诊断问题——运行框架应该允许你这样做。

<a id="where-tools-fit"></a>

## 工具的位置

在大多数智能体中，工具模式和结果是最大的单一上下文消耗来源，因此工具设计也是上下文工程决策——这正是[工具与 MCP](tools-and-mcp.md)的主题。
