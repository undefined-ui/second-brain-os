# 为什么选择 Markdown 和纯文本

格式看起来只是细节，却决定了系统能否正常工作。

<a id="agents-handle-files-better-than-apis"></a>

## 智能体处理文件比调用 API 更可靠

智能体读取文件夹时，做的正是它最擅长的事：阅读文本和编写文本。不需要学习数据模式，不需要确保 API 调用正确，也不存在某个请求只成功了一半的失败方式。

这种可靠性会在成千上万次操作中不断累积。写入 Markdown 文件的流水线，其问题可以在 diff 中看见；通过 API 写入的流水线，往往要到以后才暴露问题。

<a id="portability-is-not-theoretical"></a>

## 可迁移性不是抽象问题

人们过去信任的笔记工具，不是停运，就是改变定价，或者故意让导出变得困难。

普通文件消除了这一问题。你的知识库可以在任何文本编辑器中打开，使用任何同步工具，并配合任何能读取文件的智能体。换模型、换编辑器、换操作系统，都不会影响知识库，因为它从来没有被锁在某个工具里面。

在这里，这比平时更加重要，因为第二大脑会用数年时间积累价值。一种困住你的格式，最终可能让你失去整套积累。

<a id="wikilinks-as-a-graph-format"></a>

## 用双向链接表示图谱

`[[Page name]]` 是一种使用两种括号符号的约定，可以构成真正的图谱，直接以文本阅读，并在不理解这种语法的工具中继续保留意义；最坏的情况下，它仍然只是句子中的几个词。

你可以用正则表达式解析它，`scripts/graph_export.py` 正是这样做的。换成专有的块引用格式，试试看还能不能这么简单。

<a id="git-works-on-it"></a>

## 它可以使用 Git

文本差异。仅这一项特性，就足以让智能体能够安全地无人值守运行：它做出的每一处更改都可以审查、撤销，并追溯到某次运行。

二进制格式和基于数据库的应用没有等价能力。你要么完全信任自动化，要么不进行自动化。

<a id="the-limits"></a>

## 局限

纯文本有几件事不擅长，假装没有这些问题，只会让人最终感到沮丧。

**大规模结构化查询。** Dataview 可以覆盖很多需求，但超过几千个页面后，关系型问题需要真正的数据库。应当导出图谱，而不是放弃 Markdown；请参阅[导出图谱](../05-graphs/exporting-your-graph.md)。

**富媒体。** 图片作为文件存放在文本旁边，而不是嵌在文本里面。图表是附件。

**并发编辑。** 两个智能体同时写同一个文件，会以文件冲突的方式发生冲突——也就是说，处理起来很麻烦。

对于个人知识库，这些缺点都不足以抵消可迁移性的价值。但在真正遇到它们之前，值得提前了解。
