# Wiki 与 RAG

针对自己的文档提问，通常得到的建议是：为文档生成向量嵌入并存入向量数据库。本指南采用另一种方法，原因在于结构上的差异，而不是对工具的偏好。

<a id="the-two-approaches"></a>

## 两种方法

**RAG** 将文档分块并附上向量嵌入。问题会检索最相似的文本块，模型再依据它们回答。不写入任何新内容，语料库保持原样。

**Wiki** 将文档一次性处理成由智能体撰写并关联的页面。通过遍历这些页面回答问题。语料库因此发生转化，并持续改善。

区别在于工作发生在哪里。RAG 在每次查询时从头处理；wiki 在导入时处理一次，之后复用结果。

<a id="what-that-buys"></a>

## 你能得到什么

**理解不断积累。** 同一主题的第十份来源，会改进前九份来源共同构建的页面。在 RAG 中，第十份文档只是另一个文本块，语料库增长只会让它变大，不会让它变好。

**矛盾可以看见。** 两份意见不同的文档会生成两个文本块，但它们可能从未被同时检索到。在页面中，分歧会被明确写下、标注日期，无法被忽略。

**答案可以核查。** 页面引用了可以打开的来源。检索出来的文本块只是片段，并不包含将它们联系起来的推理。

**无需基础设施。** 没有索引，不需要重新生成向量嵌入，也不会发生存储内容与文件之间不同步的问题。

<a id="what-it-costs"></a>

## 代价是什么

**导入成本高。** 撰写页面和建立链接，需要预先消耗模型运行时间；RAG 的导入成本则几乎可以忽略。

**质量取决于导入。** 糟糕的页面规范会产生糟糕的知识库，而你往往很晚才发现。RAG 的失败发生在查询时，更容易看见。

**召回取决于链接。** 没有人链接的页面，就是图谱无法到达的页面。RAG 则仍然可以通过相似性找到它。

<a id="the-honest-position"></a>

## 坦诚的结论

对于精心整理、规模为几千页的个人语料库，这种取舍是合理的；对于无人整理的一百万份文档，则不合理。

也就是说，它适合第二大脑，不适合搜索产品；而大多数关于 RAG 的建议，都是面向后者写的。有关何时需要改变选择，请参阅[在需要时增加 RAG](../07-retrieval/rag-on-top.md)；有关检索机制，请参阅[图谱与向量嵌入](../05-graphs/graph-vs-vectors.md)。
