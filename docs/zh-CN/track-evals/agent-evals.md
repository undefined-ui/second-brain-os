# 智能体评估

单次生成是一个函数；智能体是一个过程。它会规划、调用工具、读取结果，并从自己的错误中恢复（或者无法恢复）。只评估最终答案，就像只看最后一步棋来评价整盘棋。这一页以[设计评估](designing-evals.md)为基础。

<a id="trajectories-not-just-outcomes"></a>

## 不只看结果，也看轨迹

记录完整轨迹：每一轮模型输出、工具调用、工具结果和重试。然后在两个层面评估：

- **结果**：任务是否完成，最终状态是否正确？最好对照*环境*检查（文件是否存在、数据行是否插入、测试是否通过），而不是相信智能体声称自己已经完成。智能体很擅长流畅地宣布胜利。
- **轨迹**：过程是否合理？统计步骤，检测循环，标记被悄悄忽略的工具错误。两个成功率相同的智能体并不等价，如果其中一个需要 40 轮、消耗 20 倍的令牌。

<a id="tool-call-correctness"></a>

## 工具调用正确性

最机械、回报也最高的检查包括：

- 是否为意图选择了正确工具。
- 参数是否有效，是否从上下文中正确提取（ID、日期、筛选条件——智能体经常在这里悄然失败）。
- 是否遵守顺序约束（先 `search` 后 `answer`，先 `read` 后 `write`）。
- 错误处理：在轨迹中途注入工具失败，检查智能体是否重试或报告，而不是捏造结果。

这些应是针对轨迹的代码断言，而不是评判模型调用。把 [LLM 评判者](llm-as-judge.md)留给“计划是否合理”之类的问题。

<a id="environment-based-evals"></a>

## 基于环境的评估

黄金标准是：给智能体一个沙箱环境（Docker 容器、预置数据的数据库、模拟 API），然后通过可执行检查为事后的*状态*评分。确定性的初始化、程序化的清理、没有评分歧义。构建起来比整理对话记录黄金数据集更费工夫，但对任何会改变状态的任务都值得。

<a id="harness-benchmarks-2026-edition"></a>

## 运行框架基准测试：2026 年版

公开基准测试适合比较模型和运行框架，而不是衡量你的产品——不过它们展示了优秀的基于环境评估是什么样子：

- [SWE-bench](https://www.swebench.com/) 系列——真实 GitHub 问题，由仓库自身的测试评分；SWE-bench Verified（经人工审查的 500 个用例）仍是编程智能体的主要指标，前沿模型如今已进入 80%–90% 多的区间，随着原版接近饱和，系列也不断出现更难的变体。
- [Terminal-Bench](https://www.tbench.ai/)——2.0 在真实 Docker 容器中提供 89 个经人工审查的终端任务，由可执行测试评分。它是最清晰、最值得借鉴的模板。
- [GAIA](https://arxiv.org/abs/2311.12983)——需要网页、工具和多步骤推理的通用助手任务。
- [tau2-bench](https://github.com/sierra-research/tau2-bench)——工具、智能体与模拟客户之间的*用户*交互；衡量策略约束下的对话。
- [Inspect Evals](https://github.com/UKGovernmentBEIS/inspect_evals)——在同一框架下提供上述基准的 200 多种实现。

<a id="ci-integration"></a>

## CI 集成

评估应该属于流水线，而不是笔记本：

- 每个 PR 都运行小型冒烟套件（只做确定性检查）；每晚以及发布前运行完整套件。
- 以阈值作为合并关卡；每个用例运行 N 次，并按均值判断是否放行。
- 在 CI 中固定模型版本，并把模型升级视为与其他变更一样、必须通过套件的修改。

[工具](tooling.md)一章介绍了让这些工作更轻松的方案。
