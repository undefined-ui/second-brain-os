# 用 LLM 做评判者

有些检查可以用代码完成：精确匹配、正则表达式、JSON 模式、“SQL 能否运行”。其他检查——语气、忠实度、答案是否真正回应问题——需要一个能阅读的评分者。这个评分者通常是另一个 LLM。它有用、便宜，但未经校准就不可信。

<a id="writing-the-judge-prompt"></a>

## 编写评判提示词

评判提示词是一份岗位说明，而不是愿望：

- 每个评判者只回答一个问题。“这一声明是否得到所提供上下文的支持：是／否”优于“评价整体质量”。
- 二元输出，并要求*先写理由，再给判定*。理由是你调试时的线索；先给判定的评判者会事后寻找理由。
- 提供 2–4 个完整的通过和不通过示例，尤其是边界案例。
- 给它与产品当时相同的上下文。评判 RAG 答案却看不到检索文档，只能靠猜。

提示词中的评分标准要具体：引用错误分析得出的失效分类（见[设计评估](designing-evals.md)），而不是“有帮助”或“高质量”之类形容词。

<a id="calibration-against-human-labels"></a>

## 用人工标签校准

未经校准的评判者，就是充满自信的随机数生成器。以下流程直接来自 Hamel Husain 的[评判者指南](https://hamel.dev/blog/posts/llm-judge/)：

1. 领域专家将 50–100 个输出标记为通过／不通过，并附上简短理由。
2. 在同一数据集上运行评判者，测量一致性（报告各类别的一致性，而不是原始准确率——在大多数结果良好的数据上，一个始终说“通过”的评判者也能拿到 90%）。
3. 阅读每一个分歧。修正评分标准，或者发现你自己的标签并不一致——两种情况都会发生。
4. 重复，直到一致性稳定得不再令人惊讶；此后每季度复查，并在每次更换评判模型时重新检查。

Shreya Shankar 的[谁来验证验证者？](https://arxiv.org/abs/2404.12272)从研究角度讨论了这个循环。

<a id="known-bias-failure-modes"></a>

## 已知的偏差失效模式

自 [MT-Bench 论文](https://arxiv.org/abs/2306.05685)起就已有记录，并且到 2026 年仍然存在：

- **位置偏差。** 成对比较时，评判者偏爱第一个答案（有时是第二个）。交换顺序后取平均，否则比较没有意义。
- **冗长偏差。** 正确性相同时，更长的答案得分更高。限制长度，或明确要求避免这种偏好，然后验证效果。
- **自我偏好。** 模型更偏爱自己同系列模型的输出。可行时，使用与被评模型不同的模型来评判。
- **迎合声明的意图。** 一旦附上用户自称的目标，评判者就会评价努力，而不是结果。

<a id="when-judges-lie"></a>

## 评判者何时会误判

评判者会在以下问题上悄然失败：数学和算术、小众领域事实、细微的指令违反，以及评判模型自己也会答错的任何事情。如果某项检查*能够*用代码完成，就用代码。把评判者留给真正需要语言理解的判断，始终保留人工抽查判定的机制，也绝不要让评判分数在与逐步骤检查矛盾时仍然放行发布——[智能体评估](agent-evals.md)会解释如何结合两者。
