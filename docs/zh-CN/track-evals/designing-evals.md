# 设计评估

评估的质量取决于测试用例的质量。从“我们的机器人有时会出错”走到可信赖的套件，必须经过失效模式：先说清哪里会错，再构造能够触发它的用例。这一页假设你已经完成[为什么需要评估](why-evals.md)中描述的错误分析。

<a id="golden-sets"></a>

## 黄金数据集

黄金数据集是一组固定输入，配有已知正确的预期结果，由了解产品的人精心整理。经验法则如下：

- 优先从生产执行轨迹中取材，其次才自行编造。真实输入比你能写出的任何例子都更奇怪。
- 每个有名称的失效模式，至少都要有几个历史上曾触发它的用例。
- 也要包含普通的成功案例，否则你会过度适应异常情况，导致正常流程退步。
- 将它与代码一起放入 git 做版本管理。没人能查看差异的黄金数据集，也没人会信任。

<a id="synthetic-data"></a>

## 合成数据

流量稀少时——上线前，或者针对罕见却关键的路径——可以生成用例。让 LLM 沿着你有意选择的维度变化：角色、措辞、长度、语言、对抗意图。有两点需要注意：

- 合成输入没有问题；合成*标签*却会形成循环论证。一个模型在自己编造的数据上给另一个模型打分，说明不了什么。让人工抽查标签。
- 按照一套维度模式来生成，而不是只说“给我 100 个多样化例子”，那样得到的通常是同三个想法的 100 个变体。

<a id="graded-vs-binary"></a>

## 分级评分与二元判断

优先采用二元判断。通过／不通过会迫使你定义标准，人之间的分歧也会立即显现。1–5 分的“质量”量表，大多测量的是评分者的心情；两位标注者很可能分别给同一输出 3 分和 4 分，却没有任何收获。如果某件事确实有程度之分，就拆成多项二元检查（是否引用来源：是／否；来源是否正确：是／否），而不是用一个模糊数值概括。当评分者是 [LLM 评判者](llm-as-judge.md)时，这一点尤其重要。

<a id="per-step-vs-end-to-end"></a>

## 逐步骤与端到端

单次调用没有这个问题。智能体则两种都需要：

- **端到端**：任务完成了吗？这是用户关心的数字。
- **逐步骤**：每次工具调用是否合理，检索是否返回正确文档，计划是否回应了请求？端到端失败时，这些检查能定位问题。

端到端告诉你*是否*出错；逐步骤告诉你*哪里*出错。详见[智能体评估](agent-evals.md)。

<a id="sample-sizes-that-matter"></a>

## 有意义的样本量

小套件会误导人。只有 20 个用例时，从 70% 变成 80% 只是两个例子的变化——可能只是噪声。粗略指南如下：

- 20–50 个用例：足以启动飞轮，不足以比较提示词。
- 对每个关注的失效模式准备 100–200 个用例：约 10 个百分点的差异开始有意义。
- 对随机性系统，每个用例运行多次；报告结果分布，而不是某次幸运的运行。

拿不准时，先算置信区间，再庆祝。如果区间同时跨越“改善”和“退步”，就继续收集用例，而不是发布。
