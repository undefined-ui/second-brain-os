# 为什么需要评估

评估就是 AI 产品的测试。一次提示词修改可能解决一个投诉，却悄悄破坏另外三件事；没有测量，你只能从用户那里得知。能够可靠交付 LLM 功能的团队，会把评估当作工程纪律，而不是演示前凭感觉检查一下。

<a id="vibes-vs-measurement"></a>

## 凭感觉与做测量

凭感觉开发通常是这样：调整提示词，粘贴你记得的三个例子，点点头，然后发布。周末项目这样做没问题。但一旦有真实流量，它就会崩溃，因为你采样的是自己的记忆，而不是用户的输入。

测量枯燥，却很具体：

- 一组固定、能够代表真实使用情况的输入
- 一种为每个输出自动评分的方法
- 一个在你修改内容时会随之变化的数字

有了这个数字，你才能有依据地说“新模型值得迁移”，或者“这次提示词修改让检索变差了”。

<a id="the-eval-flywheel"></a>

## 评估飞轮

这个循环大体遵循 Hamel Husain 和 Shreya Shankar 的教学方式，也与 [Anthropic 的智能体评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)一致：

1. **错误分析。** 阅读真实执行轨迹。不是仪表盘，而是实际对话记录，读三十份或一百份。每看到一个失败，都写一条简短笔记。
2. **分类体系。** 将笔记归为有名称的失效模式：“捏造订单 ID”、“忽略日期筛选”、“只道歉而不行动”。
3. **指标。** 将每个常见失效模式转成检查——字符串断言、代码测试，或者依据明确标准的 [LLM 评判者](llm-as-judge.md)。
4. **迭代。** 修复最大的失效模式，重新运行，观察数字，再带着新轨迹回到第一步。

飞轮比任何单个指标都重要。“有用程度 1–10 分”这样的通用评分什么也说明不了；从你自己的失败分类中产生的指标，才能准确告诉你该修复什么。如何把失效模式转成具体测试用例，见[设计评估](designing-evals.md)。

<a id="why-teams-skip-it-and-the-bill"></a>

## 团队为什么跳过评估，以及要付出的代价

常见借口都可以理解，但代价都很高：

- “输出是主观的，没法测试。”可以测试。主观的整体可以拆成客观的部分。
- “上线后再加评估。”上线后，你就是在生产环境中调试，让愤怒的用户替你评分。
- “看数据是苦差事。”阅读轨迹，是 AI 工程师最有价值的一小时工作。没人会把单元测试寄托给希望。

代价最终表现为打地鼠式的回归问题：每次修复都像赌博，模型升级令人恐惧，而开发速度恰好在产品开始变得重要时下降。拥有评估的团队，可以在模型发布当周就升级，因为测试套件会告诉他们哪里坏了。

从小处开始。二十个真实失败、一套分类、一个指标。剩下的交给飞轮。如果你的产品是智能体，而不是一次模型调用，请看[智能体评估](agent-evals.md)，了解额外需要的机制。
