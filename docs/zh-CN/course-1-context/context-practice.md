# 上下文实践

你已经了解底层机制和[四个位置](the-four-places.md)。本页进入实操：审计一个现有智能体，重新组织它的上下文，并在规模达到一定程度后加入两项重要改进。


> 下面的完整审计流程也已打包为技能：安装[课程插件](../../../plugins/README.md)，然后在项目中运行 `/agents-course:context-audit`。

<a id="audit-the-window"></a>

## 审计上下文窗口

对照真实智能体操作，不要凭记忆判断。

1. 捕获一个完整请求载荷：记录对话进行到中途时，框架实际发送给模型的 JSON。
2. 分别统计各部分的 token 数：系统提示词、工具定义、消息历史、检索内容、当前查询。把这五个数字记下来。
3. 圈出系统提示词里的每一个动态值：时间戳、用户名、注入的记忆。每个动态值都会确保每次调用发生缓存未命中。
4. 检查第 1 轮和第 20 轮的工具列表是否完全相同。如果运行中改变过，每次改变都意味着完整缓存失效。
5. 找出历史记录中最大的单项。它几乎总是一份原样返回的工具结果，而这里本应只保留文件路径。
6. 找到当前目标。如果它只出现在开场消息里，现在就已经落在窗口注意力较弱的中间位置。
7. 读取 API 响应里的 `cache_read_input_tokens`。对于已经预热的对话，如果这个值为零，说明前缀中的某些内容正在变化。

<a id="restructure-to-the-four-places"></a>

## 按四个位置重新组织

按顺序处理审计发现。把系统提示词精简到每次调用都成立的内容，并把圈出的所有动态值移入消息历史。在对话开始时固定工具列表；运行中需要停用工具时，改为拦截调用并返回拒绝信息，而不是移除定义。改写输出庞大的工具，让它把结果写入磁盘，只返回路径和一行回执。然后添加尾部提醒：每隔几次工具结果，追加一行当前目标。重新进行审计，那五个数字应该明显转向更短、更稳定的前缀，以及简洁的实时尾部。

<a id="switch-to-tool-search-past-twenty"></a>

## 超过二十个工具后改用工具搜索

Anthropic 的[高级工具使用](https://www.anthropic.com/engineering/advanced-tool-use)文章指出，始终加载全部定义无法持续扩展。启用工具搜索后，Opus 4 在其 MCP 评估中的得分从 49% 提升到 74%，Opus 4.5 从 79.5% 提升到 88.1%。他们自己的阈值是超过十个工具，或定义占用超过 10K token；本课程把二十个工具作为明确界限。常用的少量核心工具始终加载，其余标记为延迟加载，让模型按需搜索定义。前缀因此缩短，而根据这些数据，选择准确率也会随之提高。

<a id="add-a-summarising-subagent"></a>

## 增加负责摘要的子智能体

子智能体是一道上下文防火墙。当任务需要阅读五十个文件时，不要在主窗口中读完它们。创建一个子智能体，让它用自己的窗口消化这些文件，只交回一页摘要。主智能体保留结论，不携带全部证据。同样的模式适用于任何批量阅读：搜查日志、大型差异、成堆文档。[运行框架手册](../track-harness/context-engineering.md)介绍了如何把这种防火墙接入实际系统。

<a id="tips"></a>

## 建议

- 每三到五步，在尾部重申目标。
- 超过约 2,000 token 的工具原始结果不要留在历史里；改为路径加回执。
- 拦截工具调用，不要移除工具。
- 将系统提示词变更视为发布，并检查差异。
- 在生产环境中监控缓存指标。一次悄无声息的缓存未命中，会让这部分费用变成 10 倍。

<a id="prove-it-to-yourself"></a>

## 亲自验证

1. 在一份 30K token 的记录中间放入一个虚构事实并提问；然后把同一个事实移到最后一条消息，再问一次。比较答案。
2. 连续发送两次完全相同的请求，读取 `cache_read_input_tokens`；再在系统提示词开头加上时间戳，观察它降到零。
3. 对同样五十个文件做摘要，一次放在主窗口，一次交给子智能体；比较最终上下文大小和答案质量。
