# 在需要时加入 RAG

本指南不主张为个人知识库配备向量数据库。但这个主张有适用边界，应该把边界说清楚，而不是奉为教条。

<a id="when-it-starts-to-pay"></a>

## 什么时候开始值得

大致需要同时满足三个条件：

**规模超过几千页，** 以至于读取索引并沿链接探索不再适合现有上下文预算。

**问题采用了页面中没有使用的措辞。** 如果你经常找不到明知存在的内容，那就是召回问题，而向量嵌入正是解决这类问题的。

**语料未经你整理。** 一个在没有人判断什么重要的情况下吸收了一万份文档的知识库，没有可靠的结构可以导航，剩下的办法就是相似度。

大多数个人知识库永远不会同时达到这三个条件。我的也没有；只满足其中两个，我不会愿意增加这份维护工作。

<a id="what-to-embed"></a>

## 对什么做向量嵌入

对 wiki 页面做，而不是原始资料。

它们本身就是语义单元，由理解过内容的系统写成，每页一个概念。这正是切分试图近似、却很少真正做到的效果。再把页面切成固定长度的窗口，会破坏你已经投入成本建立的结构。

把页面标题、别名和正文一起做嵌入。在经过整理的知识库中，标题携带大量信息，因为那是你挑选的。

<a id="hybrid-not-replacement"></a>

## 混合使用，而非替代

有用的安排依然让图谱主导：

1. 向量嵌入找到入口页面，包括措辞不同的页面。
2. 图谱从这些入口沿链接扩展。
3. 智能体阅读扩展后的页面集合，并给出带引用的答案。

向量嵌入提供召回，图谱提供结构，以及两个页面相关的原因。让整个流程只靠相似度，会丢掉链接，而链接恰恰是知识库里最费心建立的部分。

<a id="keeping-the-index-fresh"></a>

## 保持索引新鲜

这是没人计算在内的维护成本。每次导入都会修改页面，过时的嵌入索引却会返回内容已经变化的页面。

把变更页面的重新嵌入放进每次导入任务，而不是另排一个计划。落后一周的索引会悄悄出错，并产生貌似合理的错误答案。

如果你觉得这份维护工作得不偿失，那么对大多数知识库来说，你的判断是对的。这也是本节写得很短的真实原因。

<a id="simpler-things-to-try-first"></a>

## 先试试更简单的办法

增加基础设施之前，先确定问题是否真在召回。

缺少别名是“找不到”的最常见原因。糟糕的索引也是。还有可能是两个月前开始，导入流程不再正确建立链接，留下越来越多任何检索方式都无法有效到达的孤立页面。

在认定自己需要向量之前，先运行 `scripts/link_check.py`，再读一遍索引。
