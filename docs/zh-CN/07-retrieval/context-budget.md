# 上下文预算

智能体每读一页都要消耗上下文，而质量在窗口填满之前就会下降。读得更多，并不等于读得更好。

<a id="progressive-disclosure"></a>

## 渐进式披露

有效的模式是：

1. **先看索引。** 每项一行，说明有哪些内容。
2. **打开真正重要的页面。** 通常是三到八页。
3. **每次沿链接前进一步，** 当新页面不再增加信息时停下。

每一步成本都很低，也为下一步提供依据。如果一开始就加载所有可能相关的材料，大部分预算会浪费在最终无关的页面上，还会把有用内容挤到长上下文中注意力最弱的中间位置。

<a id="why-not-paste-the-whole-vault"></a>

## 为什么不把整个知识库粘进去

长上下文模型能容纳大量内容，让人很想彻底跳过检索。

有两个理由不这么做。第一，注意力在长上下文中的分布并不均匀，中间材料的利用可靠性低于两端，这正是《Lost in the Middle》的发现，也是内容位置重要的原因。第二，基于全部材料生成的答案难以核查：你根本不知道它实际用了哪些页面。

引用五个你能打开核对的页面，比依赖四百个你无法逐一核查的页面得出的流畅答案更好。

<a id="summary-layers"></a>

## 摘要层

超过几百页后，可以在总索引与具体页面之间增加一级索引：每个主题领域一张简短页面，列出该领域有哪些内容，以及每页涵盖什么。

智能体先读总索引，打开相关的主题索引，再打开具体页面。这样是三次低成本读取，而不是一次昂贵的读取。

不要让摘要层不断堆积。两级足够；三级意味着你在建立一个没人维护的层级结构，而且摘要的摘要会逐渐偏离底层内容。

<a id="measuring-what-was-read"></a>

## 记录读过什么

```
List the pages you read to answer that, in the order you opened them.
```

这条指令值得偶尔运行。它能暴露两类问题：明明六页就够，智能体却读了三十页；或者知识库里有二十个相关页面，它却只看三页就回答。两者都可以通过调整指令解决，而仅看答案都发现不了。

<a id="subagents-for-wide-reads"></a>

## 用子智能体处理大范围阅读

当一个问题确实需要大量材料时，派出一个[子智能体](../06-agents/subagents.md)。它在自己的上下文中阅读并返回摘要，这样主会话只需要承担答案的上下文成本，而不用承担所有来源的成本。
