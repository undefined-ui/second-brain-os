# 评判器与黄金集

行为检查由代码实现，代码是可信赖的。端到端评分通常不是代码能完成的：“这份回复是否正确、是否有依据”，需要能够阅读内容的评分者，实践中通常就是另一个 LLM。评判器是一种测量仪器，而没有仪器一出厂就已经校准。本篇先介绍如何检查评判器，再介绍如何构建供它评分的案例集。

<a id="judges-need-judging"></a>

## 评判器也需要被评判

有两个特性决定评判器给出的数字是否有意义。

第一，与人工标注的一致性。你先亲自将输出标为通过或失败，再让评判器判断同样的输出，按类别测量一致率——一个始终回答“通过”的评判器，在大部分内容都正确的数据上也能取得 90% 的总体准确率，却发现不了任何问题。阅读每一处分歧：一半时候是评分标准模糊，另一半时候是你自己的标注不清楚。完整流程，以及已经记录在案的偏差失效模式（位置、冗长程度、自我偏好），见[以 LLM 为评判器](../track-evals/llm-as-judge.md)。

第二，多次运行的方差。让同一个评判器对相同输入重复运行几次，看看判定变化有多大。Airbnb 曾为此付出高昂代价：他们的流水线在每次评估时都重新生成模型撰写的参考答案；[其工程博客](https://airbnb.tech/ai-ml/from-weeks-to-a-day-how-we-made-llm-evaluation-fast-enough-to-iterate-on/)报告，在输入完全相同的多次标注运行之间，大约四分之三的参考答案发生了变化。分数变化两个百分点，可能意味着智能体改善了、评判器漂移了，也可能只是参考答案又随机生成了一遍——评估测量的是自己的噪声。他们的修复方案值得借鉴：以输入和配置作为键，缓存参考答案和评判器判定，让相同输入返回相同结果，只有主动要求时才重新生成。

<a id="building-the-golden-set"></a>

## 构建黄金集

黄金集是两个测试层都会运行的固定案例集合。Airbnb 的[评估驱动开发文章](https://airbnb.tech/ai-ml/eval-driven-development-lessons-from-evaluating-genai-at-scale/)建议使用 50–100 个样例，并直言其构成要求：必须包含坏样例，不能只有好样例，因为没有坏样例就无法检验辨别能力。只包含正常路径的套件，不过是在证明智能体能处理它本来就能处理的情况。

Google 的智能体质量白皮书还提出一条维护规则：每个生产环境中的失败，在捕获并标注之后，都应成为永久测试案例。失败不是什么修复后就该忘掉的难堪往事；它们是你能拥有的最高价值案例，因为每一个都对应真实用户遇到的真实边界情况。从轨迹中挖掘案例，就是[下一篇](evals-practice.md)的实践内容。

案例集不断增长时，评分机制仍要保持精简。Airbnb 的相关建议是：三到五个经过良好校准、各自针对一个正确性维度的评判器，胜过二三十个噪声很大的评判器。

<a id="production-sampling-and-set-decay"></a>

## 生产流量抽样与案例集老化

黄金集是你拍摄那一刻的用户快照，而用户一直在变化。新的表达方式会出现，新的文档类型会进入知识库，一次功能上线会改变人们的需求。六个月后，一套测试可能仍有 95% 的通过率，却只覆盖生产环境实际情况的一半。

应对办法是持续从实时流量中引入样本。Airbnb 每天抽取 5% 已去标识化的生产流量，运行程序化检查和评判器——目的不是控制版本发布，而是发现黄金集尚未包含的失败。不论规模多大，这个做法都适用：定期抽取一部分真实运行记录，评分，再将所有失败提升为黄金集案例。案例集应该每周增长一点；最新案例已经是三个月前的黄金集，就是已经老化的黄金集。

有了经过校准的评判器、包含失败案例的数据集，以及让案例集保持真实的抽样循环，测量本身才成为值得信赖的东西。[实践篇](evals-practice.md)会把这些变成一个下午就能完成的具体步骤，从你自己的智能体最近二十次失败开始。
