# 备份与可迁移性

<a id="sync-is-not-backup"></a>

## 同步不是备份

这就是整篇文章的核心，也是几乎所有人都会犯的错误。

同步只负责传播。如果自动化错误地重写了两百页，同步会在几秒内忠实地把破坏复制到所有设备上。一个文件被删除，就会从所有地方消失。

备份意味着一份不会跟着变化的副本。至少要有一份，而且要脱离同步路径。

<a id="a-workable-arrangement"></a>

## 可行的安排

**私有 Git 远程仓库，** 每次任务结束后推送。它保留版本，因此能够回答“它三周前是什么样”，这是普通文件备份做不到的。

**同步工具，** 用于跨设备工作，继续用你熟悉的那一种即可。

**定期归档，** 保存到外部存储或独立的云存储中，不与前面两项连接。每月一次足够。

保留三份副本，其中一份简单、更新慢，才能抵御现实中真正会发生的故障。

<a id="test-a-restore"></a>

## 测试恢复

至少做一次。拿出归档，把它恢复到其他位置，在 Obsidian 中打开，检查链接是否正常。

没有测试过的备份，总会在不合时宜的时刻失效。常见原因并非数据损坏，而是这时才发现归档漏了一个文件夹，或者备份恰好发生在同步中途，留下了写到一半的内容。

<a id="what-you-are-protecting-against"></a>

## 真正要防范什么

主要不是磁盘故障。磁盘故障不常见，而且同步能够应对。

真正的风险是自动化三周前悄悄做错了某件事，而你现在才发现。这需要历史记录，因此这里 Git 承担的保护作用比文件备份更大。

<a id="portability"></a>

## 可迁移性

知识库由 Markdown 和双向链接组成，因此离开某个特定工具不会带来结构性成本。值得偶尔检查的事项是：

**重要内容都存在文件里。** 插件专用元数据、画布文件、数据库导出，都可以作为附加功能，但不应承载只存在于那里的独有知识。

**离开 Obsidian，链接仍可解析。** `scripts/link_check.py` 会验证这一点，因为它自行解析双向链接。

**智能体指令位于知识库中，** 而不是某段聊天历史或应用设置里。`CLAUDE.md`、技能和命令应随文件夹一起迁移。
