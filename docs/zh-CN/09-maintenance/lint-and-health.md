# 检查知识库

结构腐化是无声的。没有报错，知识库只是逐渐回答得不好，因为三分之一的页面已经无法到达，却没有人发现。

<a id="what-a-lint-checks"></a>

## 检查哪些内容

**失效链接。** 要区分两种情况：拼写错误或重命名造成的链接，直接修复；真正的知识缺口，则加入 `index.md` 的 Gaps 部分。

**孤立页面。** 没有任何页面链接到它们。要么找到合适的位置并建立链接，要么删除。

**残缺页面。** 大约不到四十个词、没有链接的页面，通常来自失败的导入。标记后，从 `raw/` 中的原始资料重新导入。

**结构规范违规。** 缺少 frontmatter、类型错误、使用了词表之外的标签。

**近似重复。** 标题相似、别名重叠、共享入站链接。

**索引偏移。** `index.md` 中漏掉了页面，或者条目指向不存在的位置。

<a id="report-before-repairing"></a>

## 先报告，再修复

机械性修复自动执行。任何需要判断的操作都先提出建议，等待你决定。

这条界线很重要：检查器自行判断并合并页面，会破坏已有工作；只报告不修复，又会产生一份无人处理的清单。失效链接和结构规范错误可以机械处理，合并与删除则不行。

<a id="running-it"></a>

## 运行方式

```
/lint
```

每周运行一次，或者在导入大约二十份以上来源之后运行。不必每次导入都做，那样成本会超过收益。

在 Git 工作区干净时运行，这样错误修复只需一次 `git checkout` 就能撤销。

在 Obsidian 中，[Find orphaned files and broken links](https://github.com/Vinzent03/find-unlinked-files) 能以可视化方式完成孤立文件与失效链接这两项检查。

如果只想快速检查，不调用智能体：

```bash
python3 scripts/link_check.py ~/brain
```

<a id="reading-the-output"></a>

## 阅读结果

数量比单条记录更重要。一周出现三个失效链接很正常。四十个则意味着导入指令发生了变化，正在生成指向从未创建过页面的链接。

随着知识库增长，绝对数量也会增长，因此应追踪比例随时间的变化。参见[指标](../05-graphs/metrics.md)。
