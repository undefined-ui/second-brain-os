# 扩展到上千页之后

本指南大部分内容假设知识库规模为几百到几千页，个人知识库通常会在这个范围停留多年。超过之后，有些环节会开始吃力。

<a id="what-actually-breaks"></a>

## 真正出问题的是什么

**不是搜索。** ripgrep 搜索一万个 Markdown 文件仍然很快。

**不是 Obsidian，** 尽管全局图谱视图在一千个节点左右就开始失去实用性。

**检索成本。** 索引变得很长，阅读它也要消耗可观的上下文，这是第一个真正的约束。

**你的注意力。** 一千页已经超出你能在脑中掌握的范围。恰恰从这时起，知识库变得更有用，你也开始无法察觉其中某些部分已经腐化。

<a id="summary-layers"></a>

## 摘要层

解决索引问题的办法，是在总索引与具体页面之间增加一级。

每个主题领域建立一个简短页面，列出有哪些内容、每页涵盖什么。智能体先读总索引，再打开相关主题索引，最后打开具体页面。三次低成本读取，代替一次高成本读取。

两级足够。三级就意味着摘要的摘要；它们会偏离所描述的内容，又取代原文被阅读。

<a id="splitting-vaults"></a>

## 拆分知识库

当两个领域确实无法相互启发时，按领域拆分，例如工作与某项爱好，或者两个不相关的专业领域。

不要按日期或体量拆分。整个系统的价值就在于旧材料连接新材料；按时间拆分，恰恰切断了最值得保留的联系。

拆分的代价是跨领域联系不再出现，而那些联系往往最有意思。尽量晚拆，慎重拆。

<a id="archiving"></a>

## 归档

把不活跃的材料移到 `wiki/` 之外的 `archive/` 文件夹：仍保留在磁盘上，仍可用 ripgrep 搜到，但不再进入索引或图谱。

可逆性很重要，因为“不活跃”只是一种判断。归档的主题如果重新变得重要，仍可以恢复。

<a id="pruning-what-never-mattered"></a>

## 清理从来没重要过的内容

一年之后仍然只有一个来源、没有入站链接的概念页面，从来就算不上概念，只是一个段落。删除它们，能减少查询必须越过的杂项，让其他内容更好用。

每年做一次，而不是持续不断地做。

<a id="the-honest-ceiling"></a>

## 真实的上限

超过一万页的某个规模后，精心整理的 wiki 就不再适合由一个人维护，因为没人能以那个速度持续整理，而整理正是这个系统有效的原因。

如果你已经到了那里，要么知识库不再是个人的，要么导入已经在缺乏判断的情况下运行了很久。后者常见得多，解决办法在上游：重新审视你喂给它什么。
