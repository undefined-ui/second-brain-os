# 批量导入多年积累的资料

总有一天，你会想把所有东西都导进来：书签文件夹、下载目录、三年的聊天记录，以及装着八百条未读内容的稍后阅读队列。

这往往是最容易出问题的一次运行。它花费不低，耗时数小时；如果处理顺序不对，产出的 wiki 读起来像杂物堆，而不是有结构的知识体系。但它也能在一次集中处理后让知识库真正变得有用，所以值得认真做好。

<a id="order-matters"></a>

## 顺序很重要

先处理最早的资料。

原因是，较新的来源应该更新较早来源创建的页面。按这种方式运行，wiki 就能记录你的理解如何发展：某个主题最早的页面，之后的修正，再到当前立场。

如果先处理最新资料，每份旧来源都会变成需要与已经拥有最终答案的页面调和的矛盾。智能体会把精力花在调和上，历史顺序也会颠倒，你因此失去了这种结构相较搜索索引最独特的价值。

<a id="batch-always"></a>

## 始终分批处理

每批十份来源。每批结束后：更新 `index.md`，向 `log.md` 追加记录，提交更改，汇报结果。

```
/backfill raw/archive/2024
```

[`commands/`](../../../commands/README.md) 中的 `backfill` 命令就是这样工作，并在批次之间停下来等待继续指示。

分批有三个原因：在你仍能停止时，成本就清晰可见；质量始终可以检查，你能在第十页发现页面规范有问题，而不是到第四百页才发现；发生崩溃时，也只损失一个批次，而不是整次运行。

<a id="check-the-first-batch-properly"></a>

## 认真检查第一批

阅读第一批生成的每个页面，一个都不要漏。

这是发现系统性问题的时机：页面只有摘要而没有解释，概念拆分过细，链接只是装饰，frontmatter 不正确。先修正 `CLAUDE.md` 并重新运行这一批，再继续后面的工作。

第一批放过的缺陷，最终会出现在四百个页面中；事后修复的成本，比最初运行还高。

<a id="cost-control"></a>

## 控制成本

导入一千份来源会产生一笔实实在在的账单。以下方法可以控制它：

- **先筛选。** 大多数档案里，有一半是失效链接或你保存后从未打开过的东西。在导入之前，先让智能体按标题分流。
- **限制批次大小，**在扩大规模之前，观察前几批的成本。
- **跳过只需归档的资料。** 并非所有内容都需要 wiki 页面；资料留在 `raw/` 中仍然可以搜索。

<a id="dead-links"></a>

## 失效链接

旧书签导出文件往往充满已经不存在的网页。应当在导入前检查，而不是处理到一半才发现：

```bash
python3 -c "import sys,urllib.request as u;[print(l.strip()) for l in sys.stdin]"
```

对于已经下线但仍有价值的内容，Internet Archive 通常保留了副本。从那里剪藏，并在 frontmatter 中说明原始链接已经失效，因为一个 URL 返回 404 的来源页面，一年后将无法核查。

<a id="resuming"></a>

## 恢复中断的运行

处理时持续把进度写入 `log.md`，每批一行，记录覆盖的文件夹和范围。运行中途停止是迟早的事；届时根据日志恢复，而不是猜测哪些文件已经完成。

<a id="after-the-backfill"></a>

## 批量导入之后

运行一次完整的结构检查。大规模导入总会留下孤立页面、近似重复内容和损坏链接。

```
/lint
```

然后运行一次复查，看看知识库如今包含了什么。批量导入后，它知道一些你早已忘记收藏过的内容。那一刻，正是整项工作的回报。
