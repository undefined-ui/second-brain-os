# 图谱与嵌入向量

对于如何向自己的文档提问，常见建议是先生成嵌入向量，再通过相似度检索。本指南没有采用这种做法，其中的原因值得理解，而不是盲目接受。

<a id="what-each-is-good-at"></a>

## 各自擅长什么

**嵌入向量**能够找到与查询含义相近的文本，即使用词完全不同也可以。它擅长召回，不需要预先建立结构，也能处理一堆从未整理过的文档。

**图谱**能够找到存在明确连接的内容，提供可以沿着探索的方向；如果链接有类型，还能说明连接的原因。它擅长回答多跳问题，以及解释两个事物为什么相关。

<a id="where-similarity-fails"></a>

## 相似度何时会失效

它的失败方式很具体：相似度会检索出与问题相似的片段，而一个好问题的答案，往往并不与问题相似。

询问两个想法之间有什么联系时，建立这种联系的段落可能与任何一方都没有共同词汇。询问自己在哪些问题上改变过看法时，也没有任何片段会与这个问题相似，因为答案存在于两篇相隔一年写下的页面之间的关系中。

还有排序问题。二十个都只能回答一半问题的片段，会挤掉那个完整回答问题的页面，因为相似度并不理解完整性。

<a id="where-the-graph-fails"></a>

## 图谱何时会失效

召回。如果某个页面从未建立链接，图谱就无法到达它；而资料导入一旦开始马虎，链接规则恰恰最容易悄悄失守。

图谱也无法找到那些你依稀记得、却叫不出名字的内容。那属于搜索问题，而对几千页规模的知识库进行全文搜索几乎是瞬间完成的，这也是为什么 `ripgrep` 在实际中能覆盖大多数此类需求。

<a id="why-a-personal-vault-leans-graph"></a>

## 为什么个人知识库更适合图谱

有三个与这一规模直接相关的原因。

你的资料集很小。几千个页面谈不上检索难题，它只是一个文件夹。嵌入向量所需的基础设施，要到数百万文档规模才有回报，低于这个规模时成本往往大于收益。

你的资料集已经完成分块。原子化页面本身就是由理解了内容的编写者创建的语义单元。再把它们切成固定长度的块，会破坏你付出成本才建立的结构。

你的问题关注关系。我对 X 知道些什么，X 与 Y 有什么联系，有什么证据反对 Z。这些都是图查询。

<a id="hybrid-when-you-get-there"></a>

## 需要时再采用混合方案

有意义的组合是：用全文搜索或嵌入向量找到入口，再沿图谱向外扩展。

这样，搜索负责召回，图谱提供结构，各尽其长。关于何时值得承担这部分维护成本，请参阅[在需要时添加 RAG](../07-retrieval/rag-on-top.md)。
