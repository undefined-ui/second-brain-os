# GraphRAG 及其适用场景

GraphRAG 的方法是先从资料集中构建图谱，再针对图谱回答问题，而不是针对原始文本块。Microsoft Research 发布了最广为人知的版本，论文题为《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》。

其大致流程是：从每份文档中提取实体和关系，构建图谱，检测由紧密连接的实体组成的社区，为每个社区生成摘要，然后利用社区摘要回答问题，而不是利用检索到的段落。

<a id="why-it-exists"></a>

## 为什么会有这种方法

它针对的是文本块检索的一项具体弱点：无法回答有关整个资料集的问题。“这里有哪些主要主题”无法通过检索五个最相似的文本块来回答，因为没有哪个文本块包含完整答案。答案必须从所有内容中综合得出。

这类问题恰好是人们希望第二大脑回答的问题，也恰好是相似度搜索最不擅长的。

<a id="what-your-vault-already-has"></a>

## 你的知识库已经具备什么

对照一个维护良好的 wiki，再看一遍这个流程，会发现其中大部分已经建立起来了。

资料导入时编写实体页面，就是在做实体抽取。关系就是 wikilink，如果你添加了类型，它们还会带上类型。知识库本身就是图谱。缺少的是社区层：识别簇，并为这些簇生成摘要。

而这部分缺失内容，你其实也已经在手动编写对应版本。综合页面就是社区摘要，由读过来源的模型生成，而不是由对实体进行聚类的算法生成。

<a id="whether-to-run-it"></a>

## 是否应该运行它

对个人规模而言，大概不需要，坦率地说，原因就是规模。这种方法适合庞大到无法人工整理的资料集，其收益才能覆盖成本。几千个经过整理、具有真实链接的页面，并不需要自动社区检测来发现主题；你在图谱视图中就能看见这些簇。

但它可以用于审查，而不是作为检索系统。对导出的图谱运行社区检测，再把算法得到的簇与综合页面进行比较，可以发现知识库中有哪些主题尚未引起你的注意。这是一项每季度做一次的工作，无需成为基础设施。

<a id="related-research-worth-reading"></a>

## 值得阅读的相关研究

**HippoRAG** 在知识图谱上应用个性化 PageRank 来回答多跳问题，更直接地对应了智能体从起始页面沿链接向外探索的过程。

应该阅读论文本身，而不是论文摘要或二手概述。两者都明确说明了结果成立的条件，而这些条件决定了方法能否迁移到你的具体情况。
