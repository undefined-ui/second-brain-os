# 智能体还是工作流

在动手构建之前，先做一个判断：你能把步骤写下来吗？如果能，就把它们写成代码。按照已知顺序执行已知步骤的代码就是工作流。除了一个方面，工作流在其他所有方面都优于智能体。

Anthropic 的[构建高效智能体](https://www.anthropic.com/engineering/building-effective-agents)清楚地区分了两者：工作流是模型调用和工具沿着预先定义的代码路径运行的系统；智能体则由模型主导自身流程，在执行过程中决定下一步。他们的建议是找到能解决问题的最简单方案，只有在复杂性确有价值时才增加它。智能体系统用延迟和成本换取能力，这笔交换必须值得。

<a id="why-workflows-win-by-default"></a>

## 为什么默认应选择工作流

工作流更便宜：每一步只携带这一步所需的上下文，不必背着一份记录此前所有事情、不断增长的对话。它能并行运行：独立步骤可以分散执行，而循环天然是串行的，每个决策都要等待上一次观察。它也更容易调试：失败的步骤有名称、输入和日志，而失败的循环可能需要你阅读四十轮记录。各步骤还能独立测试，因此修好的问题不容易再次出现。

<a id="where-loops-earn-their-cost"></a>

## 循环何时值得付出成本

循环适用于无法预知步骤的任务。例如，研究时下一次查询取决于上一次返回的内容；调试时没人知道上千个文件中的哪一个藏着故障；开放式综合分析中，答案的形状要从材料里逐渐浮现。这些任务的共同特征是：事前无法列举分支，事后却能检查结果。如果这两个条件没有同时成立，你就是在为工作流的工作支付智能体的价格。

<a id="the-cost-reality"></a>

## 成本的现实

成本倍数并非传闻，Anthropic 用自己的实际流量公布了数据。在[我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/built-multi-agent-research-system)中，他们报告智能体通常消耗约为聊天交互 4 倍的 token，多智能体系统约为 15 倍；只有任务价值能够覆盖账单时，多智能体架构才有经济意义。同一篇文章也承认，目前需要共享上下文或智能体之间紧密协作的领域不太适合多智能体，大多数编程任务就在其中。

因此，升级阶梯应该是：一次模型调用，然后是工作流，再到单个智能体，最后才是多个智能体；每上一级，都必须说明理由。大多数系统应该在较早的位置停下。白皮书没有明确问出口的问题，本课程会先问。

## 如何学习这门课程
