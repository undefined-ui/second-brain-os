# 定时运行

定时运行会让知识库感觉像是活了起来。你醒来时，它已经归档了你剪藏的资料，发现了一处矛盾，并留下三行文字说明发生了什么变化。

但这也是在无人监督时写入你的笔记，因此顺序很重要：先把[安全护栏](safety-and-guardrails.md)设置好，再安排定时任务。

<a id="cadence-per-job"></a>

## 每项工作的频率

**资料导入，每天一次。** 夜间处理白天积累在 `raw/` 中的所有内容。每天批量处理很合适，因为这样智能体有机会发现你保存的三份资料讲的是同一个想法。每小时处理一次则做不到。

**建立链接，每周一次。** 建立联系需要先有材料。一周导入结束后再运行。

**质量检查，每周一次。** 在链接者之后运行，以发现那一轮操作造成的问题。

**复查，每周一次。** 这是你真正会阅读的输出。把它安排在你制定计划的那天早上。

**指标，每月一次。** 把四个数字追加到笔记中。参见[指标](../05-graphs/metrics.md)。

<a id="setting-one-up"></a>

## 设置一个定时任务

在 Claude Desktop 中，进入“定时任务”（Schedule）选项卡，然后新建任务：

```
Frequency:  Daily, 7:00am
Folder:     your vault
Prompt:     File anything new in raw/ into the wiki following CLAUDE.md.
            Link it to existing pages. Update index.md and log.md. Commit
            with a message naming the run. Then write me three lines on
            what changed.
```

也可以在会话中直接提出要求：“设置一个每天早上七点运行的任务，导入 raw/ 并总结发生了什么变化”。

从终端通过 `cron` 或任务计划程序调用无界面的 Claude Code，效果相同；如果你希望运行结果自动进入一次 git 提交，这种方式更合适。

<a id="what-a-run-must-produce"></a>

## 每次运行必须产出什么

每次都要有三样东西。

**一条日志。** 否则无法审计你睡觉期间发生了什么。

**一次提交。** 每次运行对应一个提交，提交信息中写明运行名称。这样一次糟糕运行只需一个命令就能回退，而不必耗费整个晚上。

**一份给你的报告。** 哪怕只有一行。一个没有任何可见输出的定时任务，会让你逐渐失去信任，随后不再查看它。

<a id="detecting-silent-failure"></a>

## 发现静默失败

失败不一定是崩溃。也可能是运行完成了，却没有做任何有用的事：来源为空、API 调用中途失败，或者指令没有匹配到任何文件。

有两个成本很低的检查。让每次运行报告数量，而不只是报告完成，这样“导入了 0 个来源”就清晰可见。另一个是每月检查一次提交频率：每日任务整整一周没有提交，意味着它可能从周二起就在悄悄失败。

<a id="start-manual"></a>

## 先手动运行

每项工作在设为定时任务前，先手动运行一周。你要确认产出的质量足够高，即使不仔细阅读也能接受，因为设为定时任务后，情况正是如此。

最后再为导入设置定时运行，因为它写入的内容最多。
