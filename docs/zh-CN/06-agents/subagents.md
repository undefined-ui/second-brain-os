# 子智能体与并行工作

子智能体在自己的上下文中运行。这正是它的意义所在：子智能体为了回答问题而阅读三十个页面时，主会话的上下文不会被这三十个页面填满，只会收到答案。

<a id="when-to-fan-out"></a>

## 何时分派并行任务

**跨多个页面研究。** 派一个子智能体去阅读某个簇，再带着总结返回。主会话可以把上下文预算留给真正的工作。

**相互独立的来源。** 十篇互不相关的文章可以顺利并行导入，因为它们不会修改相同的 wiki 页面。

**核验。** 一个智能体编写，另一个对照来源检查页面。独立上下文使检查有意义；同一个智能体重读自己的工作，大多只会赞同自己。

<a id="when-not-to"></a>

## 何时不该并行

**相关来源。** 同一个主题的三篇文章必须顺序导入。并行时，每个智能体都会独立创建概念页面，最终得到三个版本，或者其中两个被覆盖。

**任何涉及索引的工作。** `index.md` 和 `log.md` 都是单个文件，每次运行都想向其中追加内容。并行写入会产生冲突，或悄悄丢失条目。

**小任务。** 启动子智能体需要完整地建立一次上下文。只处理两个文件时，比直接完成还慢。

<a id="merging-parallel-work"></a>

## 合并并行工作

避免大多数冲突的规则是：子智能体写入互不重叠的路径，由父智能体合并。

让每个子智能体报告打算写入的内容，而不是直接修改共享文件。所有子智能体返回后，父智能体一次性更新索引和日志。只要两个子智能体从未被分配到重叠材料，页面文件本身就可以安全地并行写入。

任何并行运行前都先提交。因为一旦出错，就会同时影响许多文件。

<a id="cost"></a>

## 成本

并行不会减少总 token 用量，它减少的是实际等待时间，并保护主上下文。四个子智能体的成本大约是一个的四倍。

对于大规模历史资料补导，这种交换值得；对于每天导入五篇剪藏文章，则没有意义。
